Steel Weight Calculator

A single-file web tool that turns dimensions into weight for the sections a steel service centre handles every day, and builds a bill of materials as you go. It needs no install and no backend, so it opens instantly on a phone at the counter or on a laptop in the office.

Open the live demo

The problem

Quotes and dispatch planning need quick, consistent weights for plates, channels, beams, angles, flats, pipes and sheets. Doing it by hand or in scattered spreadsheets is slow and invites mistakes.

What it does

  • Ten product sections: plates, channels, joists and beams, purlins, roofing, equal angles, flats, decking, and round, square and rectangular hollow sections.
  • Size and thickness dropdowns pull standard weights per metre from built-in tables.
  • Plates and hollow sections are calculated from first principles.
  • Add any result to a bill of materials with a running grand total in metric tons.
  • Copy a result, print the BOM, or export it as CSV.
  • Responsive layout with a mobile BOM drawer.

How to use it

  1. Pick a product tab, for example MS Channels.
  2. Choose size and length, then enter the number of pieces.
  3. Read the weight, then press Add to BOM.
  4. Repeat across tabs, then print or export the list.

How it works

Plate (MT) = THK × WIDTH × LENGTH × NOS × 7.85 ÷ 1,000,000,000
Pipe (kg/m) = (OD − t) × t × 0.02466
Section (MT) = kg/m × length(m) × NOS ÷ 1000

I checked the outputs by hand: a 12 × 2500 × 6000 mm plate, 4 nos, comes to 5.652 MT, and 20 channels of 150 × 75 at 6 m come to 2.016 MT.

WorkNest

An internal web platform that brings employee records, leave management and visitor entry passes into one system, with role-based access for admins, HR, managers and security. This is a case study with screenshots; the source and live data stay private because it runs a real company's operations.

The problem

Leave requests, employee files and gate visitors were handled on paper and across separate tools, with no single record of who approved what.

What I built

  • Employees: profiles, document upload with automated data extraction, bulk import from Excel, and export of a profile to PDF or Excel.
  • Leave: requests, extensions, long-term leave tracking, return-to-work, and manager approval decisions with history.
  • Visitors: public registration form, host approval by secure link, a public status page for the visitor, and a QR pass.
  • Security desk: QR scan page for check-in and check-out, enforced by the server.
  • Platform: notifications centre, global search, reports, settings, and role-based access through Supabase Auth.
  • Scanner bridge: a small local Node service that lets the browser trigger a Windows scanner.

How a visit flows

Visitor registers→Host gets approval link→Host approves→QR pass issued→Security scans in / out

Engineering notes

  • API routes hold the business rules. The UI is never trusted as the access-control boundary.
  • Service-role keys are used only server-side and read from environment variables.
  • Approval links are signed so they cannot be guessed.
  • Services, UI components and API routes are kept in separate layers.

WorkNest Security

A gate-desk Android app. The guard scans a visitor's QR pass with the phone camera and the server decides whether entry or exit is allowed.

What it does

  • Signs in with a WorkNest account through Supabase Auth.
  • Scans the visitor QR with the back camera, or accepts a token typed in for testing.
  • Shows visitor, host, purpose and current status, with clear pending, rejected and success messages.
  • Calls the WorkNest scan API for scan, check-in and check-out. Rules such as no check-in before approval and no duplicate check-out live on the server.
  • Updates status live through a Supabase realtime subscription.

How to use it

  1. Guard signs in on the phone.
  2. Tap scan and point the camera at the visitor's pass.
  3. Review the details, then confirm check-in or check-out.

How it is built

The interface is a Vite and React web app wrapped as a native Android app with Capacitor, so one codebase gives both a browser preview and an installable app. Camera access uses ZXing, and permission denial is handled with a clear message.

One API, two kinds of client

Browser and Android app

The problem

The scan endpoint served the web app, which authenticates with a session cookie. A native Android app has no such cookie, so its requests would be rejected with a 401.

What I did

Let the same route accept either a cookie session or a Supabase bearer token, verified on the server. Cross-origin calls are limited to an allow-list of origins, so only the web app and the app's own webview are accepted. Role checks run after authentication in both cases, so the rules are identical for every client.

const ALLOWED_ROLES = ["ADMIN", "HR", "BOSS", "SECURITY"];
const ALLOWED_ORIGINS = new Set([
  "https://<your-web-app>.vercel.app",
  "capacitor://localhost",   // the Android app's webview
]);

const bearer = request.headers.get("authorization")
  ?.match(/^Bearer\s+(.+)$/i)?.[1];

if (bearer) {
  // Native app: verify the token with Supabase on the server
  const { data, error } = await supabase.auth.getUser(bearer);
  if (error || !data.user) return json(request, { error: "Session expired" }, 401);
  user = data.user;
} else {
  // Browser: existing cookie session
  user = (await createClient()).auth.getUser();
}

2

Approval links that cannot be guessed

Visitor approval by link

The problem

A host approves a visitor by tapping a link in a message. If the link only held a visit ID, anyone could change the ID and approve someone else's visitor.

What I did

The link carries the data plus an HMAC-SHA256 signature. The server recomputes the signature and compares it with a constant-time check, so a tampered link is rejected. The secret stays on the server in an environment variable.

node:crypto · HMAC-SHA256 · timingSafeEqual
export function createVisitorApprovalLinkToken(payload) {
  const encoded = Buffer.from(JSON.stringify(payload)).toString("base64url");
  return `${encoded}.${signature(encoded)}`;          // data.signature
}

export function verifyVisitorApprovalLinkToken(token) {
  const [data, sig] = token.split(".");
  const expected = Buffer.from(signature(data));
  const supplied = Buffer.from(sig);
  if (expected.length !== supplied.length ||
      !timingSafeEqual(expected, supplied)) return null;   // tampered
  return JSON.parse(Buffer.from(data, "base64url").toString("utf8"));
}
3

A leave rule that depends on the length

Leave day counting

The problem

The leave policy counts a leave of seven days or fewer without Sundays, but counts every calendar day for a longer one. Naive date maths can shift a day across timezones and daylight saving.

What I did

The rule lives in one small, pure function, so the form, the approval screen and the reports all agree. Dates are parsed as UTC so daylight saving and the server's timezone can never shift a day.

Pure function · UTC date maths · tested by hand
/**
 * <= 7 calendar days: Sundays are not counted.
 *  > 7 calendar days: every day counts.
 */
export function calculateLeaveDays(from, to) {
  const start = new Date(`${from}T00:00:00.000Z`);   // UTC, no timezone drift
  const end   = new Date(`${to}T00:00:00.000Z`);
  const calendarDays = Math.floor((end - start) / 86400000) + 1;
  if (calendarDays > 7) return calendarDays;
  let counted = 0;
  for (let i = 0; i < calendarDays; i++) {
    const day = new Date(start.getTime() + i * 86400000).getUTCDay();
    if (day !== 0) counted++;                          // skip Sunday
  }
  return counted;
}
// Mon-Sun (7 days) -> 6     Mon-Mon (8 days) -> 8

Show “On leave” without changing the employee record

Derived status

The problem

Marking an employee as on leave by editing their employment status means someone has to remember to change it back, and records go stale.

What I did

Employment status is never touched. The screen derives a display status from the record plus whether an approved leave covers today, using the India date so it flips at the right midnight.

Derived state · Intl.DateTimeFormat
export function getEmployeeDisplayStatus(employmentStatus, onApprovedLeave) {
  const status = String(employmentStatus ?? "UNKNOWN").trim().toUpperCase();
  if (status !== "ACTIVE") return status.replaceAll("_", " ");
  return onApprovedLeave ? "ON LEAVE" : "ACTIVE";
}

export const getIndiaDateString = (date = new Date()) =>
  new Intl.DateTimeFormat("en-CA", { timeZone: "Asia/Kolkata" }).format(date);

The server decides, the app only displays

Gate security app

The problem

If the phone app decided who could enter, a modified client could let anyone in.

What I did

The app sends the scanned token and shows what the server returns. It maps the status to a clear message for the guard, and every rule (approved before entry, no exit before entry, no double exit) is enforced by the API.

Thin client · server-side rules · Capacitor
